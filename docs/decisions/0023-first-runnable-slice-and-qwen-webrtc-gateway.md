# ADR 0023：第一段可运行代码与千问 WebRTC 握手边界

状态：部分由 ADR-0024 修订  
日期：2026-08-08

说明：第 3 项中的信令端点配置、第 5 项中的 Workspace ID 与允许模型范围，以及样例中的 Omni 专用会话配置已由 ADR-0024 修订。WebRTC 握手、安全边界和其余决策继续有效。

## 背景

产品需求和技术架构已经形成完整基线。进入业务开发前，需要先用真实浏览器验证最关键、风险最高的能力：实时语音自然度、字幕、打断、麦克风模式和网络状态。

千问 WebRTC 建连需要长期 DashScope API Key，但供应商信令端点返回的 SDP answer 可以让浏览器随后直接传输媒体。第一段代码既要可运行，也不能把密钥放进浏览器。

## 决策

1. 第一段可运行代码只建立 `apps/web`、`apps/api` 和 `packages/protocol` 三个必要工作区。数据库、任务和 MediaStore 等包等到出现第一项真实业务需求时再建立，不创建空壳包。
2. Web 使用 React、Vite 和 `vite-plugin-pwa`，提供面向技术验证的单页实时语音实验室。
3. API 使用 Fastify 接收浏览器原始 SDP offer，在服务端添加 DashScope Authorization 后转发到千问北京地域 WebRTC 信令端点，再把原始 SDP answer 返回浏览器。
4. 持续音频不经过 API；浏览器与千问建立直接 WebRTC 媒体连接。
5. API 只允许已确认的 Plus/Flash 模型，校验 Workspace ID、请求 Content-Type、SDP 大小、版本行和音频媒体段。
6. Qwen 原始事件 schema 放入共享协议包；供应商特有的浏览器连接实现隔离在 Web 的 realtime 目录，避免业务组件直接依赖事件细节。
7. PWA 新版本采用提示刷新；即使 Service Worker 发现更新，活跃通话也不自动重载。
8. 自动测试不调用真实收费模型，只覆盖确定性的协议、网关和状态转换。真实质量通过同脚本设备测试记录。

## 后果

- API Key 和 Workspace ID 不会进入浏览器构建产物；
- 媒体延迟不会因私有 API 中继而增加；
- 当前千问信令实现仍是供应商专用代码，完成真实验证后再提炼稳定的 Provider Adapter；
- 完整断线恢复、持久化和家庭账号不属于这个技术样例，后续仍需实现；
- 先得到可测的关键体验，避免在模型链路没有验证前投入大量业务代码。
